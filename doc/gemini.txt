三、 关键硬核模块深化设计
3.1 核心 IM 链路：如何保证消息“不丢、不乱、不重”
这是后端面试最经典的高频战场，系统设计必须做到滴水不漏。

1. 消息发送与投递流程（以群聊为例）
客户端 A 发送消息，携带一个本地生成的 client_msg_id（用于去重和前端展示占位）。

网关接收：后端收到消息，先去 Redis 判定 client_msg_id 是否已存在（防止重试导致的重复发送）。

双轴定序：调用 Redis INCR seq:group:{gid} 获取该群的绝对递增序号（Sequence ID），同时生成全局唯一雪花 ID。

异步持久化与广播：

消息异步写入 MySQL。

消息同步写入 Redis ZSet（缓存最近 100 条消息）。

将消息投递到 Redis Stream (Stream_Group_Mailbox)。

多节点路由：所有服务节点都在消费这个 Redis Stream。发现属于自己节点上在线用户的群消息，立即通过 WebSocket 推送给用户。

亮点话术： “我们没有使用传统的内存广播，而是基于 Redis Stream 实现了分布式的消息路由总线。这样长连接网关可以无状态地任意水平扩展，且保证了并发环境下群聊消息的绝对递增顺序。”

2. 断线重连与“消息漫游”补盲
当校园网络切换（如从食堂走到教学楼断网重连），客户端会触发重连逻辑：

前端本地记录了当前收到的最大 Sequence ID（例如 seq = 105）。

重连成功后，前端向后端发送 HTTP 请求：/message/sync?groupId=xxx&lastSeq=105。

后端优先读取 Redis ZSet，如果 ZSet 里的最大 Seq 大于 105，直接把增量消息一次性打包返回（网速极快）；如果缓存失效，则走 MySQL 索引兜底。

前端收到补盲消息后进行客户端排序，实现无缝平滑刷新。

3.2 智能 Agent 异步削峰工作流
如果把大模型调用直接写在长连接的事件响应里，群里多点几次 @AI，系统立刻就会卡死。系统采用基于生产者-消费者模型的 Agent 工作流：

客户端发送 `@AI 帮我总结` 
     │
     ▼
WebSocket 接收 ──► 立即向群内广播一条“占位消息”（AI 正在思考中...）
     │

Agent-as-User 落地支持： AI 的数据库实体就是 user_id = 0。当 AI Worker 线程拿到大模型回复后，会调用统一的 MessageService.send(fromUserId=0, toGroupId=xxx)。这样，AI 的回复完美走通了 3.1 节设计的所有消息存储、排序和多节点广播逻辑。

二、 核心模块深化设计方案
2.1 长连接网关与消息投递模块（同学 B 负责）
拒绝使用高大上但难以控制底层的 STOMP，直接采用 Spring 原生 WebSocketHandler，配合 Redis Stream 做分布式消息路由总线 。

1. 核心交互流程（时序设计）
第 1 步【客户端发送】：客户端 A 通过 WS 连接向服务端发送 JSON 消息，携带 client_msg_id。


第 2 步【去重与定序】：服务端拦截消息，利用 Redis SETNX 检查 client_msg_id 防止重发。验证通过后，调用 INCR seq:chat:{chat_id}，生成该会话内绝对连续递增的 Sequence ID 。

第 3 步【双写与发布】：

异步写库：将消息丢入异步线程池，写入 MySQL。


热数据同步：将消息存入 Redis ZSet（chat:msg:{chat_id}），以 seq_id 作为 Score，只保留最近 100 条 。


总线广播：将消息发布到 Redis Stream 频道 。

第 4 步【跨节点消费】：所有集群节点（通过集群或单机多端口部署）都在监听该 Redis Stream。一旦收到消息，节点检查本地 UserSessionManager，若接收方用户连接在本节点，立即通过底层 TCP 连接推送到客户端。

2. 断线重连与漫游补盲机制
[断网重连成功] ──► 客户端发送 HTTP 请求: /api/msg/sync?chat_id=X&last_seq=105

2. 前端健壮性策略
心跳双向维系：每 25 秒由前端发送一条紧凑的 PING 字符串，后端必须在 5 秒内回复 PONG。若超时，前端主动执行 close() 并触发断线重连状态机。

滑动窗口排序：由于前端可能在重连时同时收到 WS 推送和 HTTP 补盲包，前端收到任何消息后，必须根据 seq_id 执行二分法插入排序，彻底杜绝 UI 层的消息乱序交织。

二、 安全与复合权限模块 (security)
这里不采用简单的“管理员/普通用户”粗粒度控制，而是实现一套贴合校园业务的三维复合权限体系 。

1. 核心鉴权组件

JWT 过滤器 (JwtAuthenticationFilter)：拦截所有 HTTP 请求，解析 Header 中的 Token，并将用户信息存入 UserContextHolder（基于 ThreadLocal），实现上下游无状态调用 。

2. 三维权限 AOP 设计
系统需要同时判断用户的全局角色、操作的资源类型（普通群/班级群/课程群）、以及用户在该群内的群身份 。我们通过自定义注解 @GroupPermission 和 AOP 切面来实现统一校验 。

核心设计代码逻辑：

Java
// 1. 定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface GroupPermission {
    MemberRoleEnum[] requiredRoles() default {MemberRoleEnum.MEMBER}; // 默认需要群成员身份
    GroupTypeEnum[] allowGroupTypes() default {}; // 允许操作的群类型
}

// 2. 切面实现 (GroupPermissionAspect)
@Aspect
@Component
public class GroupPermissionAspect {
    @Before("@annotation(groupPermission)")
    public void checkPermission(JoinPoint joinPoint, GroupPermission groupPermission) {
        // 1. 从 ThreadLocal 获取当前用户 ID
        // 2. 解析方法参数，提取 targetGroupId
        // 3. 查询数据库/缓存，获取该群的类型 (GroupType) 和用户在该群的身份 (MemberRole)
        // 4. 执行交叉比对：
        //    - 如果是学生角色，拦截创建“班级群”和“课程群”的请求。
        //    - 如果群类型不在 allowGroupTypes 范围内，抛出 GroupPermissionException。
        //    - 如果群内身份低于 requiredRoles，抛出 GroupPermissionException。
    }
}
这套机制让你的 Controller 层极其干净，一行权限判断代码都不用写。

三、 WebSocket 网关与消息流水线模块 (websocket & message)
这是整个系统最值钱、面试最能打的部分。我们彻底抛弃 STOMP，采用 Spring 原生 WebSocket + Redis Stream + 双轴定序架构 。

1. 长连接网关层 (websocket 包)
负责维持客户端与服务端的物理连接。


UserSessionManager：维护一个并发安全的 ConcurrentHashMap<Long, WebSocketSession>，记录当前节点上连接了哪些用户 。处理心跳保活（Ping/Pong），如果检测到掉线则清除 Session。


MessageDispatcher：所有客户端发来的消息统一进入这里。它负责解析 JSON，根据指令类型路由给具体的 Service 处理 。

2. 消息双轴定序与投递流程 (message 包)
当 MessageDispatcher 收到一条群聊消息时，触发以下严格的硬核流水线：

Step 1: 去重 (Deduplication)
利用 Redis 的 SETNX client:msg:{client_msg_id} 指令（设置 5 分钟过期）。如果返回 false，说明是前端网络抖动造成的重复发送，直接丢弃 。

Step 2: 双轴定序 (Sequencing)
调用 Redis INCR seq:chat:{chat_id}，生成该群内绝对连续递增的 Sequence ID 。同时调用 SnowflakeIdGenerator 生成全局唯一的雪花 ID 作为主键 。

Step 3: 异步持久化 (Async Persistence)
将消息本体推入 Spring 的异步线程池，写入 MySQL 的单表（利用 chat_id 和 seq_id 的联合索引保证查询极速） 。

Step 4: 热缓存漫游 (ZSet Cache)
将消息存入 Redis ZSet chat:msg:{chat_id}，以 seq_id 为 Score，保留最近 100 条。这保障了用户断网重连拉取最新消息时，直接击中内存，保护数据库 。

Step 5: 集群总线广播 (Redis Stream)
将封装好的消息 JSON 投递到 Redis Stream 频道 。

Step 6: 本地消费与推送 (Push)
所有 Spring Boot 节点都在监听这个 Stream。当节点监听到消息时，去自己的 UserSessionManager 里查找接收方用户。如果用户在自己这台机器上，调用 session.sendMessage() 推送出去 。

这套架构完美解决了“消息丢失、消息乱序、多节点无法通信”三大分布式 IM 痛点。

这三个底层模块构成了系统的“通信与安全底座”。只有这套底座坚如磐石，后续的 AI 异步协作和群组业务才能顺畅运转。

四、 AI Agent 异步削峰工作流模块 (modules/ai)
1. 为什么要设计异步削峰？
大模型（如 DeepSeek、Qwen）的 API 响应通常需要 3~10 秒 。如果群聊中有多人同时触发 @AI，直接在 WebSocket 的 I/O 线程或主业务线程中同步等待 HTTP 响应，网关的线程池会瞬间被榨干，导致整个系统的长连接大面积卡死甚至雪崩 。

为此，我们必须设计一套基于动态占位符、阻塞队列与独立线程池隔离的异步工作流。

2. 核心工作流详细设计
整个 AI Agent 触发到响应的过程分为 4 个高度解耦的步骤：

Step 1：拦截与占位符生成（生产者）
当消息流水线（Message Pipeline）收到一条群消息时，MentionParser 解析器检测到内容命中 @AI。

业务线程绝不阻塞，而是立即调用 MessageService 向群内广播一条特殊的占位消息（例如：内容为“AI 正在思考中...”，msg_type = MessageTypeEnum.AI_PLANNING） 。

记录下这条占位消息的 seq_id 或 msg_id。

将请求封装为 AiTask 对象，投递到内部的阻塞队列中。

Step 2：任务队列与工作线程池隔离（削峰）
构建一个独立的 AiWorkerPool，与网关的 I/O 线程池完全隔离。

Java
@Configuration
public class AiThreadPoolConfig {
    @Bean(name = "aiTaskExecutor")
    public Executor aiTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);       // 根据购买的 API 并发限制微调
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(500);    // 环形缓冲阻塞队列
        executor.setThreadNamePrefix("ai-worker-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.DiscardOldestPolicy()); // 满了丢弃最早的
        executor.initialize();
        return executor;
    }
}
Step 3：上下文重组与大模型调用（智能体消费）
工作线程从队列中唤醒并认领任务后，执行以下核心逻辑：


拉取历史上下文：AI 模块直接调用 Redis 工具类，从 ZSet 缓存（chat:msg:{chat_id}）中逆序拉取最近 5 轮的历史聊天记录 ，送入 ConversationMemory 动态重组为标准的 Chat Context（规避换设备丢历史的问题）。

Prompt 模板渲染：根据群组类型（如课程群、实验室群），自动套用系统预设的 System Prompt 模板（例如：“你现在是计算机原理课程的助教机器人...”）。


阻断/流式发起请求：调用适配了多模型的统一客户端 LLMClient（屏蔽底层 DeepSeek 或 Qwen 的切换细节） 。

Step 4：Agent-as-User 统一推回（回调落库）
大模型生成完毕后（或通过 SSE 流式分块结束），工作线程不需要自己去触碰长连接 Session，而是直接调用通用的消息发送接口：

Java
// AI 在系统的实体即为 user_id = 0
MessageDTO aiResponse = MessageDTO.builder()
        .chatId(task.getChatId())
        .fromUid(0L)  // Agent-as-User 的核心体现 [cite: 16, 39]
        .content(llmResultText)
        .msgType(MessageTypeEnum.AI_ANSWER.getCode())
        .replaceMsgId(task.getPlaceholderMsgId()) // 携带需要被替换的占位符ID
        .build();

messageService.send(aiResponse);
这样，AI 的回复完美继承了普通用户发消息的所有底层逻辑（自动触发 Redis INCR 产生 Sequence ID 、写库、写 ZSet 缓存 、通过 Redis Stream 进行多节点集群广播 ）。

五、 校园场景的策略模式群组模块 (modules/group)
1. 为什么要使用策略模式？
在真实的校园业务中，创建群聊绝不是简单的“往数据库插入一条群记录”。不同的群，其准入限制、自动化拉人逻辑完全不同：


普通群：学生自由组建，点击直接创建 。

班级群：必须由班长或辅导员触发，且需要联动校园行政班级档案，自动把该行政班级的所有在册学生全部拉入群内。


课程群：教师一键创建，传入一个课程代码，系统必须去排课表、选课表里做多表联查，自动把选了这门课的多个班级、所有学生批量导入群内 。

如果把这些复杂的业务逻辑全部塞进一个 createGroup 方法里，代码会充斥着大量的 if-else 地狱，极难维护。我们采用工厂模式 + 策略模式（Strategy Pattern）进行优雅解耦 。

2. 策略模式架构设计
首先，抽象出统一的群组创建策略接口：

Java
public interface GroupCreateStrategy {
    // 返回群组组建结果
    GroupVO create(GroupCreateDTO dto, Long operatorId);
    // 标识当前策略支持的群组类型

}
接下来，实现三个独立的策略类，各司其职：

① 课程群组建策略 (CourseGroupStrategy)

@Service("courseGroupStrategy")
public class CourseGroupStrategy implements GroupCreateStrategy {
    @Autowired
    private GroupMapper groupMapper;
    @Autowired
    private EducationInfoMapper eduMapper; // 模拟教务系统防腐层
    
    @Override
    @Transactional(rollbackFor = Exception.class)
    public GroupVO create(GroupCreateDTO dto, Long operatorId) {
        // 1. 鉴权：通过 operatorId 判定当前操作者在教务系统中是否为该课程的授课教师
        // 2. 物理落库：生成群信息，写入 im_group 表 
        Long groupId = snowflakeIdGenerator.nextId();
        
        // 3. 核心亮点逻辑：根据选课档案自动拉人 
        // 跨表联查：根据 course_id 查询 select_course_relation，拉取所有选课学生ID
        List<Long> studentIds = eduMapper.selectStudentIdsByCourseId(dto.getCourseId());
        
        // 4. 批量异步/同步插入 im_group_member 表
        groupMemberMapper.batchInsertMembers(groupId, studentIds, MemberRoleEnum.MEMBER.getCode());
        // 5. 将教师本人设为群主
        groupMemberMapper.insertMember(groupId, operatorId, MemberRoleEnum.OWNER.getCode());
        
        return GroupVO.from(groupId, dto.getGroupName());
    }

    @Override
    public GroupTypeEnum getGroupType() { return GroupTypeEnum.COURSE; }
}
② 工厂动态路由 (GroupStrategyFactory)
利用 Spring 的依赖注入特性，在项目启动时自动将所有策略注册到 Map 中，彻底干掉 if-else：

Java
@Component
public class GroupStrategyFactory {
    // Spring 会自动将所有实现了 GroupCreateStrategy 的 Bean 注入到这个 Map 中
    private final Map<GroupTypeEnum, GroupCreateStrategy> strategies = new ConcurrentHashMap<>();

    @Autowired
    public GroupStrategyFactory(List<GroupCreateStrategy> strategyList) {
        for (GroupCreateStrategy strategy : strategyList) {
            strategies.put(strategy.getGroupType(), strategy);
        }
    }

    public GroupCreateStrategy getStrategy(Integer typeCode) {
        GroupTypeEnum type = GroupTypeEnum.getByCode(typeCode);
        GroupCreateStrategy strategy = strategies.get(type);
        if (strategy == null) {
            throw new BusinessException("未找到对应的群组组建策略");
        }
        return strategy;
    }
}
在 Controller 层中，调用变得极其丝滑：

Java
@PostMapping("/create")
public Result<GroupVO> createGroup(@RequestBody GroupCreateDTO dto) {
    Long operatorId = UserContextHolder.getUserId(); // 从 ThreadLocal 获取 [cite: 17, 18]
    // 动态获取策略并执行
    GroupCreateStrategy strategy = groupStrategyFactory.getStrategy(dto.getType());
    GroupVO vo = strategy.create(dto, operatorId);
    return Result.success(vo);
}
六、 补充：分布式环境下的数据最终一致性思考
在面试时，面试官极有可能针对 Part 1 和 Part 2 结合追问：“你在消息流水线里又是写 MySQL，又是写 Redis ZSet，又是发 Redis Stream ，如果中途有一步挂了导致数据不一致（例如 DB 成功但 Redis 失败），你怎么处理？”

为了让这个模块化单体方案在面试时具备无懈可击的防御力，我们提供一套“轻量级本地事务+重试监听器”的兜底机制：

强一致性事务边界：
在接收消息时，DB 持久化和 Redis INCR（双轴定序）作为同一个本地事务执行（或者优先让 Redis INCR 成功获取 seq_id ，再作为唯一索引字段写入 MySQL ）。如果 MySQL 报错触发唯一键冲突（说明去重失败或定序异常），事务直接回滚，向前端返回失败。

异步补偿事件流 (listener)：
当 MySQL 持久化成功后，通过 Spring 的 ApplicationEventPublisher 发布一个 MessageSavedEvent 。
由独立的 MessageSavedListener 异步监听该事件 ，专门去负责“写入 Redis ZSet 缓存” 和 “向 Redis Stream 发送广播” 。如果 Redis 偶发性网络抖动失败，监听器会触发配置好的 Spring Retry 重试机制（重试 3 次）。若依然失败，则记录死信日志（Log），由定时任务 scheduler 进行每分钟的增量数据比对补盲。
