# 麦思哲（MaiSiZhe）数据库详细设计方案

## 1. 数据库概述

### 1.1 数据库选型
- **数据库**: MySQL 8.0
- **字符集**: utf8mb4
- **排序规则**: utf8mb4_unicode_ci
- **存储引擎**: InnoDB
- **设计范式**: 第三范式(3NF)

### 1.2 设计原则
1. **遵循3NF**: 避免数据冗余,保证数据一致性
2. **合理索引**: 根据查询场景设计联合索引,提升查询性能
3. **字段优化**: 选择合适的数据类型,节省存储空间
4. **扩展性考虑**: 预留扩展字段,支持未来功能迭代
5. **安全性**: 敏感字段加密存储(password使用BCrypt)

### 1.3 数据库命名规范
- **表名**: 小写字母+下划线,如 `im_message`
- **字段名**: 小写字母+下划线,如 `user_id`
- **主键**: 统一使用 `id`
- **外键**: `{关联表}_id`,如 `group_id`
- **索引名**: `idx_{字段名}`,如 `idx_user_id`
- **唯一索引**: `uk_{字段名}`,如 `uk_username`

## 3. 表结构详细设计

### 3.1 用户模块

#### 3.1.1 用户表(user)

**用途**: 存储系统用户基本信息

```sql
CREATE TABLE `user` (
  `id` bigint NOT NULL COMMENT '用户ID(雪花算法生成)',
  `username` varchar(50) NOT NULL COMMENT '用户名(登录用)',
  `password` varchar(100) NOT NULL COMMENT '密码(BCrypt加密)',
  `student_no` varchar(20) DEFAULT NULL COMMENT '学号/工号',
  `real_name` varchar(50) DEFAULT NULL COMMENT '真实姓名',
  `avatar` varchar(255) DEFAULT NULL COMMENT '头像URL',
  `email` varchar(100) DEFAULT NULL COMMENT '邮箱',
  `phone` varchar(20) DEFAULT NULL COMMENT '手机号',
  `class_no` varchar(20) DEFAULT NULL COMMENT '班级号(学生)',
  `department` varchar(50) DEFAULT NULL COMMENT '院系',
  `role` tinyint NOT NULL DEFAULT 0 COMMENT '角色:0-学生,1-教师,2-管理员',
  `status` tinyint NOT NULL DEFAULT 1 COMMENT '状态:0-禁用,1-正常',
  `last_login_time` datetime DEFAULT NULL COMMENT '最后登录时间',
  `last_login_ip` varchar(50) DEFAULT NULL COMMENT '最后登录IP',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`) USING BTREE COMMENT '用户名唯一索引',
  UNIQUE KEY `uk_student_no` (`student_no`) USING BTREE COMMENT '学号唯一索引',
  KEY `idx_class_no` (`class_no`) USING BTREE COMMENT '班级号索引(用于班级群组建)',
  KEY `idx_email` (`email`) USING BTREE COMMENT '邮箱索引',
  KEY `idx_phone` (`phone`) USING BTREE COMMENT '手机号索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户表';
```

**字段说明**:
- `id`: 使用雪花算法生成的全局唯一ID,避免自增ID暴露业务信息
- `username`: 登录用户名,唯一约束
- `password`: BCrypt加密后的密码,长度100足够
- `student_no`: 学号或工号,用于校园身份识别
- `class_no`: 班级号,格式如"22计科1班",用于自动组建班级群
- `role`: 角色字段,控制权限等级
- `status`: 软删除标记,便于账号管理

**索引设计理由**:
- `uk_username`: 登录时快速查询用户
- `uk_student_no`: 添加好友时通过学号搜索
- `idx_class_no`: 创建班级群时批量查询同班学生

#### 3.1.2 好友表(friend)

**用途**: 存储用户好友关系

```sql
CREATE TABLE `friend` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `user_id` bigint NOT NULL COMMENT '用户ID',
  `friend_id` bigint NOT NULL COMMENT '好友ID',
  `remark` varchar(50) DEFAULT NULL COMMENT '备注名',
  `is_pinned` tinyint NOT NULL DEFAULT 0 COMMENT '是否置顶:0-否,1-是',
  `sort_order` double NOT NULL DEFAULT 0 COMMENT '排序权重(用于拖拽排序)',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '添加时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_friend` (`user_id`, `friend_id`) USING BTREE COMMENT '好友关系唯一约束',
  KEY `idx_friend_id` (`friend_id`) USING BTREE COMMENT '好友ID索引(反向查询)',
  KEY `idx_user_pinned` (`user_id`, `is_pinned`) USING BTREE COMMENT '置顶查询索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='好友关系表';
```

**字段说明**:
- `user_id`: 当前用户ID
- `friend_id`: 好友用户ID
- `remark`: 备注名,优先显示备注而非昵称
- `is_pinned`: 置顶标记,前端展示时置顶会话排在前面
- `sort_order`: 浮点数排序权重,支持灵活插入(如1.5可以插在1和2之间)

**索引设计理由**:
- `uk_user_friend`: 防止重复添加好友
- `idx_friend_id`: 查询"谁加了我"的场景
- `idx_user_pinned`: 快速获取用户的置顶好友列表

**双向好友关系说明**:
如果A和B是好友,需要插入两条记录:
```sql
INSERT INTO friend (user_id, friend_id) VALUES (A, B);
INSERT INTO friend (user_id, friend_id) VALUES (B, A);
```

### 3.2 群组模块

#### 3.2.1 群组表(im_group)

**用途**: 存储群组基本信息

```sql
CREATE TABLE `im_group` (
  `id` bigint NOT NULL COMMENT '群组ID(雪花算法)',
  `name` varchar(100) NOT NULL COMMENT '群名称',
  `type` tinyint NOT NULL COMMENT '群类型:0-普通群,1-班级群,2-课程群',
  `owner_id` bigint NOT NULL COMMENT '群主ID',
  `avatar` varchar(255) DEFAULT NULL COMMENT '群头像URL',
  `announcement` text COMMENT '群公告',
  `course_id` bigint DEFAULT NULL COMMENT '课程ID(仅课程群使用)',
  `class_no` varchar(20) DEFAULT NULL COMMENT '班级号(仅班级群使用)',
  `member_count` int NOT NULL DEFAULT 0 COMMENT '成员数量(冗余字段,便于统计)',
  `max_members` int NOT NULL DEFAULT 500 COMMENT '最大成员数',
  `is_disbanded` tinyint NOT NULL DEFAULT 0 COMMENT '是否已解散:0-否,1-是',
  `disband_time` datetime DEFAULT NULL COMMENT '解散时间',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  KEY `idx_owner_id` (`owner_id`) USING BTREE COMMENT '群主ID索引',
  KEY `idx_type` (`type`) USING BTREE COMMENT '群类型索引',
  KEY `idx_class_no` (`class_no`) USING BTREE COMMENT '班级号索引',
  KEY `idx_course_id` (`course_id`) USING BTREE COMMENT '课程ID索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='群组表';
```

**字段说明**:
- `type`: 群类型,决定建群权限和管理逻辑
  - 0: 普通群(任何人可创建)
  - 1: 班级群(仅本班学生可创建,自动拉入全班)
  - 2: 课程群(教师创建,自动拉入选课学生)
- `course_id`: 课程群关联的课程ID
- `class_no`: 班级群关联的班级号
- `member_count`: 冗余字段,避免每次COUNT(*)查询
- `max_members`: 群人数上限,不同类型群可设置不同上限

**索引设计理由**:
- `idx_owner_id`: 查询"我创建的群"
- `idx_type`: 按类型筛选群组
- `idx_class_no`: 查找某个班级的所有班级群

#### 3.2.2 群成员表(group_member)

**用途**: 存储群组成员关系及角色

```sql
CREATE TABLE `group_member` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `group_id` bigint NOT NULL COMMENT '群组ID',
  `user_id` bigint NOT NULL COMMENT '用户ID',
  `role` tinyint NOT NULL DEFAULT 0 COMMENT '角色:0-普通成员,1-管理员,2-群主',
  `group_nickname` varchar(50) DEFAULT NULL COMMENT '群昵称(覆盖全局昵称)',
  `is_pinned` tinyint NOT NULL DEFAULT 0 COMMENT '是否置顶该群:0-否,1-是',
  `sort_order` double NOT NULL DEFAULT 0 COMMENT '排序权重',
  `mute_until` datetime DEFAULT NULL COMMENT '禁言截止时间(NULL表示不禁言)',
  `join_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '入群时间',
  `quit_time` datetime DEFAULT NULL COMMENT '退群时间(NULL表示在群)',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_group_user` (`group_id`, `user_id`) USING BTREE COMMENT '群成员唯一约束',
  KEY `idx_user_id` (`user_id`) USING BTREE COMMENT '用户ID索引(查询用户加入的群)',
  KEY `idx_group_role` (`group_id`, `role`) USING BTREE COMMENT '群内角色查询索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='群成员表';
```

**字段说明**:
- `role`: 群内角色
  - 0: 普通成员
  - 1: 管理员(可踢人、改公告等)
  - 2: 群主(最高权限,可转让)
- `group_nickname`: 群昵称,允许用户在群内使用不同于全局昵称的名称
- `is_pinned`: 用户是否置顶该群,个性化设置
- `mute_until`: 禁言功能,到期自动解除
- `quit_time`: 软删除标记,保留历史记录

**索引设计理由**:
- `uk_group_user`: 防止重复入群
- `idx_user_id`: 查询"我加入了哪些群"
- `idx_group_role`: 快速查找群主和管理员

**特殊说明**:
- AI机器人作为特殊成员,user_id=0,role=0,不可被踢出
- 退群时不删除记录,设置quit_time,保留历史消息关联性

### 3.3 消息模块

#### 3.3.1 消息表(im_message)

**用途**: 存储所有聊天消息(私聊+群聊)

**重要设计决策**: 不使用按月分表,采用单表+联合索引设计

```sql
CREATE TABLE `im_message` (
  `id` bigint NOT NULL COMMENT '消息ID(雪花算法)',
  `chat_id` varchar(64) NOT NULL COMMENT '会话ID(私聊:p_uid1_uid2, 群聊:g_gid)',
  `seq_id` bigint NOT NULL COMMENT '会话内序列号(连续递增,用于排序和补盲)',
  `from_uid` bigint NOT NULL COMMENT '发送者ID(0表示AI机器人)',
  `to_uid` bigint DEFAULT NULL COMMENT '接收者ID(私聊时有值)',
  `group_id` bigint DEFAULT NULL COMMENT '群组ID(群聊时有值)',
  `content` text NOT NULL COMMENT '消息内容',
  `msg_type` tinyint NOT NULL DEFAULT 0 COMMENT '消息类型:0-文本,1-图片,2-文件,3-AI摘要,99-AI思考中',
  `mentioned_users` json DEFAULT NULL COMMENT '@的用户ID列表(JSON数组)',
  `is_recalled` tinyint NOT NULL DEFAULT 0 COMMENT '是否撤回:0-否,1-是',
  `recall_time` datetime DEFAULT NULL COMMENT '撤回时间',
  `extra_data` json DEFAULT NULL COMMENT '扩展数据(存储消息元信息)',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_chat_seq` (`chat_id`, `seq_id`) USING BTREE COMMENT '会话序列号唯一约束',
  KEY `idx_from_uid` (`from_uid`) USING BTREE COMMENT '发送者索引',
  KEY `idx_group_id` (`group_id`) USING BTREE COMMENT '群组ID索引',
  KEY `idx_to_uid` (`to_uid`) USING BTREE COMMENT '接收者索引(私聊)',
  KEY `idx_create_time` (`create_time`) USING BTREE COMMENT '时间索引(用于清理旧消息)'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='消息表';
```

**核心设计思路**:

1. **chat_id设计**:
   - 私聊: `p_{uid1}_{uid2}` (uid1 < uid2,保证双向一致)
   - 群聊: `g_{gid}`
   - 示例: `p_1001_1002`, `g_5001`

2. **seq_id双轴定序**:
   - 每个会话(chat_id)内独立递增
   - 通过Redis INCR生成,保证绝对连续
   - 客户端根据seq_id判断是否丢包

3. **联合索引uk_chat_seq**:
   - InnoDB聚簇索引特性使相同chat_id的消息物理存储紧凑
   - 查询历史消息时顺序扫描,性能极高
   - 示例查询:
     ```sql
     SELECT * FROM im_message 
     WHERE chat_id = 'g_5001' AND seq_id > 100 
     ORDER BY seq_id ASC 
     LIMIT 50;
     ```

4. **JSON字段**:
   - `mentioned_users`: 存储@的用户列表,如`[1001, 1002]`
   - `extra_data`: 存储扩展信息,如图片尺寸、文件大小等

**索引设计理由**:
- `uk_chat_seq`: 核心索引,保证消息顺序性和唯一性
- `idx_from_uid`: 查询"我发送的消息"
- `idx_group_id`: 查询群消息(虽然chat_id已包含,但单独索引便于统计)
- `idx_create_time`: 定时清理旧消息(如保留1年)

**为什么不按月分表**:
1. 跨月查询复杂(用户查看历史记录可能跨越月底)
2. 校园规模下,单表千万级数据完全能抗住
3. 联合索引已经能保证高效查询
4. 分表增加运维复杂度,收益不明显

**示例数据**:
```sql
-- 私聊消息
INSERT INTO im_message VALUES 
(100001, 'p_1001_1002', 1, 1001, 1002, NULL, '你好', 0, NULL, 0, NULL, NULL, NOW(), NOW()),
(100002, 'p_1001_1002', 2, 1002, 1001, NULL, '你好啊', 0, NULL, 0, NULL, NULL, NOW(), NOW());

-- 群聊消息
INSERT INTO im_message VALUES 
(200001, 'g_5001', 1, 1001, NULL, 5001, '@AI 帮我解释红黑树', 0, '[0]', 0, NULL, NULL, NOW(), NOW()),
(200002, 'g_5001', 2, 0, NULL, 5001, '红黑树是一种自平衡二叉查找树...', 0, NULL, 0, NULL, NULL, NOW(), NOW());

-- AI思考中占位消息
INSERT INTO im_message VALUES 
(200003, 'g_5001', 3, 0, NULL, 5001, 'AI正在思考中...', 99, NULL, 0, NULL, NULL, NOW(), NOW());
```

#### 3.3.2 私聊已读游标表(private_read_cursor)

**用途**: 记录私聊消息的已读位置

```sql
CREATE TABLE `private_read_cursor` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `user_id` bigint NOT NULL COMMENT '用户ID',
  `peer_id` bigint NOT NULL COMMENT '对方用户ID',
  `last_read_seq_id` bigint NOT NULL DEFAULT 0 COMMENT '最后已读消息的seq_id',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_peer` (`user_id`, `peer_id`) USING BTREE COMMENT '用户对唯一约束'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='私聊已读游标表';
```

**使用方式**:
- 用户A查看与B的聊天记录时,更新`last_read_seq_id`为当前看到的最大seq_id
- 计算未读数: `SELECT COUNT(*) FROM im_message WHERE chat_id='p_A_B' AND seq_id > last_read_seq_id`

#### 3.3.3 群聊已读游标表(group_read_cursor)

**用途**: 记录用户在群内的已读位置

```sql
CREATE TABLE `group_read_cursor` (
```

## 4. 索引优化策略

### 4.1 索引设计原则

1. **最左前缀原则**: 联合索引`(a,b,c)`可以支持`a`、`(a,b)`、`(a,b,c)`查询
2. **避免索引失效**: 
   - 不在索引列上使用函数
   - 避免`LIKE '%xxx'`(前导模糊)
   - 避免类型隐式转换
3. **覆盖索引**: 查询字段都在索引中,避免回表
4. **索引选择性**: 选择性高的字段放前面

### 4.2 核心索引分析

#### 4.2.1 消息表索引

```sql
-- 核心联合索引
UNIQUE KEY `uk_chat_seq` (`chat_id`, `seq_id`)

-- 典型查询1: 获取群聊历史消息
SELECT * FROM im_message 
WHERE chat_id = 'g_5001' AND seq_id > 100 
ORDER BY seq_id ASC 
LIMIT 50;
-- 使用uk_chat_seq索引,效率极高

-- 典型查询2: 获取私聊历史消息
SELECT * FROM im_message 
WHERE chat_id = 'p_1001_1002' AND seq_id > 50 
ORDER BY seq_id ASC 
LIMIT 50;
-- 同样使用uk_chat_seq索引

-- 典型查询3: 查询用户发送的消息
SELECT * FROM im_message 
WHERE from_uid = 1001 
ORDER BY create_time DESC 
LIMIT 20;
-- 使用idx_from_uid索引
```

#### 4.2.2 群成员表索引

```sql
-- 核心联合索引
UNIQUE KEY `uk_group_user` (`group_id`, `user_id`)
KEY `idx_user_id` (`user_id`)

-- 典型查询1: 查询群内所有成员
SELECT * FROM group_member WHERE group_id = 5001;
-- 使用uk_group_user的最左前缀

-- 典型查询2: 查询用户加入的所有群
SELECT * FROM group_member WHERE user_id = 1001 AND quit_time IS NULL;
-- 使用idx_user_id索引

-- 典型查询3: 查询群主和管理员
SELECT * FROM group_member WHERE group_id = 5001 AND role IN (1, 2);
-- 使用idx_group_role联合索引
```

### 6.2 定期备份策略

```bash
#!/bin/bash
# backup.sh - MySQL定时备份脚本

BACKUP_DIR="/data/backups"
DATE=$(date +%Y%m%d_%H%M%S)
DB_NAME="maisizhe"

mysqldump -u root -p${DB_PASSWORD} \
  --single-transaction \
  --routines \
  --triggers \
  ${DB_NAME} | gzip > ${BACKUP_DIR}/${DB_NAME}_${DATE}.sql.gz

# 保留最近30天的备份
find ${BACKUP_DIR} -name "${DB_NAME}_*.sql.gz" -mtime +30 -delete
```

```sql
-- 每月执行一次,清理1年前的消息(可选)
```

## 10. 总结

本数据库设计方案针对校园IM系统的特点,采用了以下核心设计:

1. **单表设计**: 消息表不使用按月分表,通过联合索引保证查询性能
2. **双轴定序**: chat_id + seq_id保证消息顺序性和唯一性
3. **JSON字段**: 灵活存储扩展信息,避免频繁表结构变更
4. **软删除**: 关键业务数据不物理删除,保留历史记录
5. **冗余字段**: member_count等字段减少JOIN查询
6. **合理索引**: 根据查询场景设计联合索引,避免索引滥用

该方案在校园规模(1000-5000用户)下能够稳定运行,具备良好的扩展性和维护性。
